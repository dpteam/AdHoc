# Ретранслятор игрового трафика (PPSSPP relay)

Сервер умеет то, что в PPSSPP называется **aemu_postoffice**: обе стороны подключаются
**наружу** к нам по TCP, а мы пересылаем байты игры. Никто ни к кому не «дозванивается»
напрямую — значит, NAT, CGNAT и hairpin перестают иметь значение.

```
PPSSPP A ──TCP 27313──▶ DPT.PSP relay ◀──TCP 27313── PPSSPP B
             (только исходящие соединения, как в DPTDOOM2 relay)
```

## Зачем

Adhoc-протокол знакомит игроков: сервер отдаёт каждому IP-адрес пира, и дальше PPSSPP
шлёт UDP напрямую. Это ломается в трёх типовых случаях:

- **NAT hairpin.** Играешь со своего же внешнего адреса изнутри LAN (или через домен,
  который резолвится в этот адрес). Роутер подменяет источник на свой LAN-IP
  (`192.168.1.1`), сервер честно раздаёт его пирам, и те стучатся в роутер, а не в тебя.
- **Строгий NAT / CGNAT.** Порт не пробросить, UPnP выключен, доступа к роутеру нет.
- **Два игрока за одним роутером** через внешний адрес.

Релей решает все три: данные идут через сервер, а не напрямую.

## Настройка PPSSPP

1. **Настройки → Сеть → «Try to use server-provided packet relay» = Да**
   (в `ppsspp.ini`: `AdhocServerRelayMode = 1`).
   Либо добавьте хост в `RelayAdhocServerList`.
2. **`AdhocUseUdp` оставьте выключенным** (по умолчанию `False`). Релей у нас TCP;
   при `AdhocUseUdp=Yes` клиент пойдёт ENet/UDP и не сможет подключиться — сервер
   напишет об этом предупреждение в лог.
3. Адрес adhoc-сервера — как обычно. Порт релея клиент берёт сам: PPSSPP жёстко
   использует **27313** (`AEMU_POSTOFFICE_PORT`), отдельного поля в настройках нет.

Проверка: в PPSSPP при старте ad hoc появится «Connected to relay», а в нашей админке
в верхней панели счётчик `relay` станет больше нуля.

## Смешанный режим — почему «видят игру, но не друг друга»

Relay — это **выбор каждого клиента**, а не свойство сервера. Если один игрок в relay,
а второй в P2P, они физически не встретятся: relay-клиент отправляет данные только через
сервер, а P2P-клиент шлёт UDP на IP из лобби (а там у relay-клиента может быть адрес
роутера после hairpin). Симптом ровно как в жизни: лобби общее, игроки в списке есть,
но друг друга не видят.

Поэтому: **либо relay включён у всех, либо ни у кого**.

Сервер это теперь замечает: если в группе есть и те, и другие, в админке появляется
событие `hint` («Mixed transports…»), а у игроков — чипы `relay` / `p2p`.
Проверка идёт не раньше чем через 10 секунд после создания группы (сокеты создаются
не мгновенно), повтор — не чаще раза в 2 минуты на группу.

## Что делает сервер

- Слушает **TCP 27313** (настраивается `relay.port`, но PPSSPP ждёт именно 27313).
- Держит сессии по MAC+порту: PDP (широковещательные датаграммы) и PTP (надёжные потоки).
- Для PDP переписывает в кадре адрес отправителя на настоящий MAC+порт и пересылает
  получателю; для PTP сводит две TCP-сессии в один туннель и гоняет байты в обе стороны.
- Ничего не знает про игру: байты внутри кадра — для него непрозрачны.

### Протокол (для будущих правок)

Little endian, как в `aemu_postoffice` (ветка `ppsspp`):

```
INIT (24 байта): int32 type | src[8] | u16 sport | dst[8] | u16 dport
  type 0 = PDP, 1 = PTP_LISTEN, 2 = PTP_CONNECT, 3 = PTP_ACCEPT, 4 = PDP_UNRELIABLE

PDP:  dstMac[8] | u16 dport | u32 size | payload        (14 + size)
      сервер меняет dstMac/порт на MAC/порт отправителя

PTP_LISTEN получает 10 байт: srcMac[8] | u16 sport      (входящий запрос)
PTP_CONNECT получает 10 байт: peerMac[8] | u16 peerPort (после accept)
PTP_ACCEPT получает 10 байт: peerMac[8] | u16 peerPort  (сразу после INIT)
PTP данные: u32 size | payload, просто пересылаются в обе стороны
```

Ключи сессий: `PDP <mac> <port>`, `PTP_LISTEN <mac> <port>`,
`PTP_CONNECT <src> <sport> <dst> <dport>`, `PTP_ACCEPT <src> <sport> <dst> <dport>`.
Соединитель ждёт listener до 2 секунд (PPSSPP тоже ретраит), accept — до 20 секунд.

## Настройки (`config.ini`, секция `[relay]`)

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `enabled` | `true` | включить релей |
| `port` | `27313` | порт (PPSSPP ждёт именно его) |
| `bindAddress` | `0.0.0.0` | адрес прослушивания |
| `maxSessions` | `512` | одновременных сессий (у одного игрока их несколько) |
| `maxPerIp` | `128` | сессий с одного IP |
| `idleSeconds` | `600` | простой несвязанной сессии |
| `lifetimeSeconds` | `43200` | жёсткий предел жизни сессии |
| `maxPdpBytes` | `16384` | максимальный PDP-кадр |
| `udpProbe` | `true` | ловить UDP/ENet на этом порту и подсказывать про `AdhocUseUdp` |

Фаервол: `tools\firewall.cmd` добавляет правило `DPT.PSP Relay` (TCP 27313, любые источники) —
внешние игроки должны достучаться до релея, иначе туннель не построится.

## Детект hairpin в админке

Сервер знает свои шлюзы (`NetworkInterface`). Если источник входа игрока совпадает
со шлюзом этой машины — это почти наверняка hairpin: игрок пришёл через внешний адрес,
а роутер подменил источник. В этом случае:

- в лог уходит предупреждение с подсказкой включить релей;
- в админской доске у игрока появляется чип **hairpin**;
- в ленте событий — заметка `hint` (без звука).

Публичная доска этого не показывает (и вообще не знает про IP).

## Границы

- **Не шифрует.** Как и оригинальный postoffice, сервер видит открытый игровой поток.
  Для случайных напарников это надо помнить; для своей компании — норм.
- **TCP, а не UDP.** При плохом канале возможен head-of-line blocking; задержка растёт,
  но lockstep-игры это переживают лучше, чем полное отсутствие связи.
- **Трафик на сервере.** Релей ест канал: игра на двоих — единицы килобайт в секунду,
  но это уже ваш трафик.
- **Клиент должен согласиться.** Сервер не может «заставить» PPSSPP использовать релей:
  это настройка клиента (`AdhocServerRelayMode`). Если у игрока она выключена — он
  играет напрямую, как раньше.
- **UDP/ENet не поддержан.** `AdhocUseUdp=Yes` в PPSSPP не совместим с этой реализацией.

## Проверка

```powershell
powershell -ExecutionPolicy Bypass -File tools\test-relay.ps1
```

Скрипт поднимает PDP-сессии, проверяет переписывание MAC/порта и доставку полезной нагрузки,
проходит полный PTP-handshake (listen → connect → accept), гоняет байты в обе стороны,
проверяет закрытие пары и отбрасывание мусорного INIT.
