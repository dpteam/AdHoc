IP пирам, те стучатся в роутер — игра «видит лобби, но не коннектит».

Сделано:

- [x] **PPSSPP relay (aemu_postoffice)** на TCP `27313`: полноценный сервер протокола
      (INIT/PDP/PTP_LISTEN/PTP_CONNECT/PTP_ACCEPT), PDP-кадры с переписыванием MAC/порта,

      `AdhocServerRelayMode=Yes` / `RelayAdhocServerList`, `AdhocUseUdp=No`.
      Реализация: `Net/RelayServer.cs`, протокол и настройка — `docs/RELAY.md`.
- [x] **Детект NAT hairpin**: если источник игрока совпадает со шлюзом этой машины
      (`Core/LocalNetwork.cs`), в лог идёт предупреждение, в админской доске у игрока
      появляется чип `hairpin`, в ленте — событие `hint` (без звука). Публичная доска
      этого не показывает.
- [x] Настройки `[relay]` в `config.ini` (enabled/port/bind/лимиты/idle/lifetime),
      UDP-проба порта с подсказкой «выключите AdhocUseUdp».
- [x] Релей под присмотром supervisor'а, отдельный статус в консоли и в `/api/status`

- [x] `tools/firewall.cmd` добавляет правило `DPT.PSP Relay` (TCP 27313) рядом с adhoc/public/admin.

## Итерация 5 — Port offset: почему «лобби есть, а сессии в игре нет»

Живой лог с реальной игры (Worms Open Warfare 2, ты + друг):

```
"PDP a4:bd:94:a8:d2:96 1"        <- offset 0
"PDP 00:02:02:02:02:02 10001"    <- offset 10000
pdp 2817 (2817 dropped) | in 137.85 KB out 0 B
```

Оба в одной группе, оба «в релее», обе стороны шлют килобайты — и ни один кадр не
доставлен. Причина: PPSSPP прибавляет свой **Network → Port offset** ко всем портам,
поэтому клиенты с разными offset'ами живут в разных пространствах портов, а релей
искал сессию по точному номеру порта.

- [x] **Нормализация ключей сессий** по модулю 10000 (`10001 → 1`, `15911 → 5911`)
      для PDP, PTP_LISTEN, PTP_CONNECT, PTP_ACCEPT (+ fallback «единственная сессия
      этого MAC нужного типа» для некруглых offset'ов).
- [x] **Перевод портов при доставке**: в PDP-кадре порт отправителя сдвигается на
      `delta = порт получателя − порт назначения` (ровно разница offset'ов); в PTP
      notice/ack порты считаются в системе координат получателя (формулы сверены
      с `AdhocTransportRelay.cpp`: `offset_port_simple` / `reverse_port_simple`).
      Ключ `[relay] portTranslation=true`.
- [x] **Диагностика дропов**: `NotePdpDrop` — один `hint` в админку на MAC в минуту
      («no relay session for that player → у получателя релей выключен»), плюс
      `NotePortTranslation` («port offsets differ (delta 10000) …»).
- [x] **Смешанный режим без ложных срабатываний**: игры пересоздают PDP-сокеты при
      пересборке лобби, поэтому игрок считается relay-клиентом ещё 30 c после
      последней сессии (`LastActivityForMac`) — иначе на 4-секундном разрыве
      вылетал ложный «Mixed transports».
- [x] Тест `tools/test-relay.ps1` дополнен сценарием из живого лога
      (`1` ↔ `10001`, оба направления) — 24 проверки.
- [x] `docs/RELAY.md`: раздел «Разные Port offset — главная причина…», ключ
      `portTranslation` в таблице настроек; README: строка в «Решение проблем».

Проверено: relay 24/24, протокол 10/10, веб-тесты зелёные; группа с двумя
relay-игроками больше не даёт ложный `hint`.

## Итерация 8 — PSP2: пустое имя группы, статистика за всё время, «Показать все»

### Пустое имя группы (Phantasy Star Portable 2)

Лог: `requested invalid group name "" hex=00 00 00 00 00 00 00 00`, игра при этом
выглядит рабочей, но часть сценариев ломается. Причина: `sceNetAdhocctlCreate(NULL)`
в PPSSPP отправляет CONNECT с восемью нулями, а референсный сервер
(`proAdhocServer.cpp`, `connect_user`) считает такое имя **валидным**
(`if (group->data[i] == 0) break;`). Мы же требовали минимум один символ.

- [x] `Util.IsValidGroupName`: пустое имя разрешено, всё остальное — только `A-Z a-z 0-9`.
- [x] `Util.GroupDisplayName`: пустая комната показывается как `Groupless` — в логе,
      событиях, админке, `/status.xml` и `/data.json` (PPSSPP и так трактует
      `Groupless` как «игроки ждут»), поэтому в фиде она не выглядит как отдельная комната `""`.
- [x] Тест `test-client.ps1`: CONNECT с 8 нулями → приходит `CONNECT_BSSID`.

### Статистика, которая переживает перезапуск

- [x] `Core/StatsStore.cs` + `data/stats.json` (атомарная запись tmp+move, раз в 15 c при
      изменениях и при выходе). Хранит: пик онлайна, число запусков, суммарные сессии,
      время в игре, трафик, таймауты, по каждой игре — пик, число входов, сессий, время,
      первый/последний визит, плюс последние 500 завершённых сессий.

## Итерация 12 — разбор Sega Rally: `000000001` это Game Share, а не баг

Жалоба: «Sega Rally показывает ID `000000001` и ad hoc не работает, в остальных играх ок».

### Что в логе

```
18:57:59  LOGIN DartPower ... game=000000001 (000000001)
18:57:59  group "GameShar" created in 000000001
18:57:59  DartPower joined 000000001/GameShar
18:58:01  DartPower left group GameShar (client-request)   ← через 1.5 с
18:58:02 … 18:58:06  ещё 4 попытки: LOGIN и сразу закрытие (in=145 B, out=0 B)
```

Три факта:

1. **В игре был один игрок.** За всё это окно в логе только `DartPower`
   (192.168.1.1), второго участника нет вообще — 18:37 и 18:49 тоже одиночные.
   Первая сессия получила `CONNECT_BSSID` (out=7 B — ровно наш ответ), подождала
   1.5 секунды, никого не нашла и вышла. Это и есть «не работает».
2. **`GameShar` = `GameShare`**, обрезанное до 8 байт (`GroupNameSize`). Значит
   игра вошла в режим **Game Share / «Обмен игрой»**.
3. **`000000001` — это код Game Share, а не наш выдуманный ID.** Подтверждение
   в исходниках PPSSPP (`Core/HLE/proAdhoc.h`):
   `uint8_t data[ADHOCCTL_ADHOCID_LEN]; // Air Conflicts ... is using "000000001" for GameSharing?`
   И PPSSPP отправляет в LOGIN именно DISC_ID из PARAM.SFO (`sceNet.cpp`),
   то есть значение пришло от клиента, сервер его только записал.

Настоящие ID Sega Rally в базе есть: `ULES00910`, `ULES00911`, `ULJM05302`,
`ULUS10311`. Режим Game Share намеренно использует отдельный код, чтобы хосты
обмена и хосты полной игры не смешивались в одном лобби.

### Что сделано (диагностика, а не «фикс» — чинить было нечего)

- [x] `GameDatabase.SyntheticNames`: `000000001` → **«Game Share (demo mode)»**,
      `IsSynthetic()` для проверок. В лобби и `/data.json` больше не висит голое
      число, `known=true`.
- [x] При LOGIN с синтетическим кодом — предупреждение в лог и `hint` в админку:
      оба игрока должны быть в одном режиме, иначе не встретятся.
- [x] При LOGIN с неизвестным кодом (демо/хомбрю/перепакованный rip) — отдельная
      строка в логе, чтобы не путать с Game Share.
- [x] `GroupEntry.EverJoined` + проверка при выходе: если игрок создал комнату,
      был в ней один и ушёл раньше 20 секунд — в лог и в ленту уходит
      «was alone in X for Ns and left — the game found no peers». Это ловит самый
      частый ложный «баг ad hoc»: тест в одиночку.
- [x] Тест: в веб-набор добавлен Game Share держатель, проверяется, что
      `000000001` отображается как «Game Share (demo mode)» и считается известным.
- [x] `docs/RELAY.md`: раздел «Game Share (`000000001`)» — что это, почему режимы
      не смешиваются, почему гостю нужен ретранслятор.
- [x] README: строка в «Решение проблем».

- [x] `canCallApi()` + `App.authOk`, который ставится **по ответам сервера**:

- [x] `logTick`, `chatPoll`, `visitPing` уважают флаг. После неудачного входа —
